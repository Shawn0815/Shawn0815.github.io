## Abstract

查詢慢常常不是 SQL 寫錯，而是資料庫看了太多資料（Full Table Scan）。
Index 是資料庫額外建的一份有順序的目錄，讓它能直接跳到目標範圍。
要建在選擇性高、常拿來查詢的欄位上；Composite Index 的欄位順序要照查詢方式排（最左前綴）。
Index 會讓寫入變慢、多佔空間，不是越多越好。

範例的查詢計畫在本機 `sqlite3 3.54.0` 用 `EXPLAIN QUERY PLAN` 跑過。

---

## Index 是什麼

目錄裡存兩樣東西：建 index 的欄位值（index key），和原始資料的位置（通常是 Primary Key）。
資料庫先查目錄，再回去拿對應的資料。

關聯式資料庫的 index 通常是 B-Tree / B+Tree，一種有順序、多層的結構。
查 `WHERE user_id = 999` 時不是從 1 比到 999，而是沿著樹直接跳到 999 附近。

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 123;
-- → SCAN orders                                                      沒有 index：全表掃描

CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 123;
-- → SEARCH orders USING INDEX idx_orders_user_created (user_id=?)    有 index：直接定位
```

---

## 什麼欄位適合建

判斷方式：這個 index 能不能讓資料庫少掃資料、少排序、少比對？

- 常出現在 `WHERE`、`JOIN`、`ORDER BY` 的欄位。
- 選擇性（Selectivity）高的欄位：`email`、`user_id` 值很分散，一查就縮到很小的範圍。
- 選擇性低的欄位效果有限：`status`、`is_deleted` 只有幾種值，用了 index 還是要看一大堆資料。

`LIKE` 要看開頭是否固定：

```sql
EXPLAIN QUERY PLAN SELECT * FROM books WHERE title LIKE 'Java%';
-- → SEARCH books USING COVERING INDEX idx_books_title (title>? AND title<?)

EXPLAIN QUERY PLAN SELECT * FROM books WHERE title LIKE '%Java%';
-- → SCAN books
```

B-Tree 照順序排，開頭固定時能轉成一個範圍去查；開頭不固定就不知道從哪裡開始，只能全表掃描。
SQLite 的 `LIKE` 預設不分大小寫，要先 `PRAGMA case_sensitive_like = ON` 才會用到一般的 index（其他資料庫看欄位的 collation）。

## Composite Index

多個欄位一起建一個 index，最常見的是「先篩選再排序」：

```sql
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at);
```

這份 index 先按 `user_id` 排，同一個 `user_id` 裡再按 `created_at` 排。
查某個使用者的訂單並依時間排序時，資料庫直接拿到已經排好的資料，不用另外排序：

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 123 ORDER BY created_at DESC;
-- → SEARCH orders USING INDEX idx_orders_user_created (user_id=?)
```

沒有可用的 index 時，計畫會多一步排序：

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders ORDER BY amount DESC;
-- → SCAN orders
-- → USE TEMP B-TREE FOR ORDER BY
```

### 最左前綴（Leftmost Prefix）

**查詢條件要從 Composite Index 的第一個欄位開始用，才吃得到 index。**
`(user_id, created_at)` 單獨查 `user_id` 可以，單獨查 `created_at` 不行：

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE created_at > '2026-01-01';
-- → SCAN orders
```

欄位順序的原則：等值查詢、選擇性高的放前面，排序或範圍查詢的放後面。

---

## 代價

Index 是多建一份資料結構換讀取速度，是讀寫之間的取捨：

- 多佔儲存空間。
- 每次 `INSERT` / `UPDATE` / `DELETE` 都要連帶更新相關的 index，寫入變慢。
- Index 越多，維護成本越高。

依實際的查詢頻率決定要不要建，不是看到欄位就加。
