## Abstract

關聯式資料庫把 User、Order 這些不同概念拆成不同的表，避免資料重複和更新不一致；查詢時再用 `JOIN` 依關聯欄位把它們配對回來。
寫 `JOIN` 最容易錯的是：`JOIN` Key 寫錯、`LEFT JOIN` 的右表條件放錯位置，以及沒發現一對多把資料展開，導致後面的統計重複計算。

範例在本機 `sqlite3 3.54.0` 跑過，`-- →` 後面是實際輸出。

---

## 基本結構

```sql
SELECT u.name, o.id AS order_id
FROM users u              -- 從 users 開始
JOIN orders o             -- 把 orders 接進來
    ON u.id = o.user_id;  -- 配對方式
```

`ON` 決定左表的一列要跟右表的哪些列配對。
寫之前先確認哪個是 Primary Key、哪個是 Foreign Key：這裡是 `users.id`（User 的 PK）對 `orders.user_id`（指向 User 的 FK）。

**不要因為兩張表都有 `id` 就寫 `ON users.id = orders.id`**，`orders.id` 是訂單自己的 id。

多張表常有同名欄位（`id`、`status`、`created_at`），用 Table Alias 標清楚來源。

---

## INNER JOIN vs LEFT JOIN

範例資料：users 有 Amy、Bob、Cindy、Dan；orders 有 Amy 的 101（paid）、102（pending），Bob 的 103（paid）。

| | 保留什麼 | 沒配對到時 |
|---|---|---|
| `INNER JOIN`（`JOIN`） | 只留兩邊都配對成功的列 | 整列消失 |
| `LEFT JOIN` | 左表全部保留 | 右表欄位補 `NULL` |

題目出現「所有使用者」「即使沒有訂單也要顯示」，就要想到 `LEFT JOIN`。

### 查 A 有、B 沒有

例如從沒下過訂單的使用者：先 `LEFT JOIN` 保留所有使用者，沒訂單的人右表欄位是 `NULL`，再留下這些列。

```sql
SELECT u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;
-- → Cindy
-- → Dan
```

也可以用 `NOT EXISTS` 表達同一件事。

---

## ON vs WHERE

- `ON`：決定兩張表怎麼配對。
- `WHERE`：`JOIN` 完之後，留下哪些列。

`INNER JOIN` 放哪邊結果通常一樣，**`LEFT JOIN` 的右表條件放在 `WHERE` 會把左表沒配對到的列過濾掉**。

需求：所有使用者，以及他們已付款的訂單。

```sql
-- 錯：Cindy、Dan 的 o.status 是 NULL，被 WHERE 濾掉了
SELECT u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 'paid';
-- → Amy   101
-- → Bob   103

-- 對：右表的限制放在 ON，只有 paid 才接得上，左表全部保留
SELECT u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o ON u.id = o.user_id AND o.status = 'paid';
-- → Amy   101
-- → Bob   103
-- → Cindy
-- → Dan
```

## Row Grain

Row Grain 是「一列資料代表什麼」。
`JOIN` 前後都要確認，因為一對多會把資料展開，後面的 `COUNT`、`SUM`、`AVG` 都是對展開後的列計算。

```txt
users        一列 = 一位 User
orders       一列 = 一張 Order
users JOIN orders → 一列 = 一位 User 的一張 Order（Amy 有兩張就出現兩次，這是正常的）
```

orders 一列一張訂單，`amount = 500`；order_items 有兩筆屬於 101。
`JOIN` 之後一列變成一筆 Order Item，訂單層級的 500 也被複製成兩列：

```sql
SELECT o.id, SUM(o.amount) AS total_amount
FROM orders o
JOIN order_items oi ON o.id = oi.order_id
GROUP BY o.id;
-- → 101   1000
```

訂單金額其實只有 500，這就是 Double Count。
解法是先把細表整理到主表的粒度再 `JOIN`。

### DISTINCT 不能修 Row Grain

「哪些使用者下過訂單」，`JOIN` 後 Amy 出現兩次，`SELECT DISTINCT u.id, u.name` 可以去掉。
但只要多選了 `o.id`，每列都不同，`DISTINCT` 就沒作用。

`DISTINCT` 只能去掉完全相同的輸出列，不會改變 `JOIN` 的 Row Grain。
**看到重複先確認 Row Grain，不要直接加 `DISTINCT` 蓋過去。**

只是要判斷「有沒有」時，`EXISTS` 更直接：

```sql
SELECT u.id, u.name
FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

## 多表 JOIN

先找出關聯路徑，再一張一張接：

```txt
users.id → orders.user_id
orders.id → order_items.order_id
order_items.product_id → products.id
```

```sql
SELECT u.name, o.id AS order_id, p.name AS product_name, oi.quantity
FROM users u
JOIN orders o       ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p     ON oi.product_id = p.id;
```

Many-to-Many 透過 Bridge Table 接兩次，例如 students → student_courses → courses。

### JOIN Explosion

一個 Product 有 3 筆 Order Item、4 筆 Review，兩張都直接接到 Product 上，會產生 3 × 4 = 12 列，因為每筆 Order Item 都會跟每筆 Review 組合。

原因通常是：

- 一對多或多對多 `JOIN`。
- 同時接好幾張一對多的表。
- `JOIN` Key 寫錯或條件不完整。

結果是查詢變慢、統計重複、API 回傳過多資料。
所以每接一張表都要確認：

- `JOIN` Key 對不對。
- 關係是一對一、一對多，還是多對多。
- 一列現在代表什麼，筆數合不合理。
- 後面的統計會不會 Double Count。

---

## 寫 JOIN 的步驟

1. 決定結果的一列要代表什麼（一位 User？一張 Order？一筆 Order Item？）。
2. 找出 Primary Key、Foreign Key，以及表之間怎麼連。
3. 題目主要要保留的資料放左邊（「所有部門」→ departments 放左邊）。
4. 選 `JOIN` 類型：
   - 兩邊都要有：`INNER JOIN`。
   - 左表全部保留：`LEFT JOIN`。
   - A 有 B 沒有：`LEFT JOIN` + `WHERE B.id IS NULL`。
5. 寫 `ON parent.id = child.parent_id`。
6. 其他條件：
   - 決定怎麼配對的放 `ON`。
   - 過濾結果的放 `WHERE`。
   - `LEFT JOIN` 又要保留左表時，右表的限制放 `ON`。
7. 檢查 Row Grain、筆數、是否會 Double Count、是否真的需要 `DISTINCT`。

多表 `JOIN` 時，明確列出需要的欄位，不要 `SELECT *`。
