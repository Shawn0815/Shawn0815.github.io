## Abstract

JWT（JSON Web Token）把身份資訊直接放進 Token，格式是 `Header.Payload.Signature`。
它的安全性不是「資料看不到」，而是「資料不能被竄改」，關鍵在 Signature。
最大的限制是發出去之後、過期之前很難讓它立即失效。

---

## 結構

三段用 `.` 分開：

```json
// Header：簽章演算法和 Token 類型
{ "alg": "HS256", "typ": "JWT" }

// Payload：身份資訊
{ "userId": 123, "role": "USER", "exp": 1750000000 }

// Signature：用 Header + Payload + Secret Key 算出來
```

**Payload 只是 Base64 編碼，不是加密**，任何人都解得開，不能放密碼、信用卡這類敏感資料。

---

## 為什麼可信

Server 簽發時用 Secret Key 算出 Signature。
Client 帶著 JWT 來時，Server 重算一次，跟 Token 裡的一致就代表內容沒被改過。

把 Payload 的 `role: USER` 改成 `role: ADMIN`，因為沒有 Secret Key，重算出來的 Signature 對不上，驗證就失敗。

---

## 存在前端哪裡

| 位置 | 風險 |
|---|---|
| LocalStorage | JavaScript 讀得到，網站有 XSS 漏洞時 Token 會被偷 |
| Cookie（`HttpOnly` + `Secure` + `SameSite`） | JavaScript 讀不到、只走 HTTPS，但要另外防 CSRF |

LocalStorage 怕 XSS，Cookie 要注意 CSRF。

---

## 最大的問題

Session 可以在 Server 直接刪掉；JWT 不存在 Server，只要 Signature 正確、還沒過期，Server 就會接受。
**Token 被偷之後，在過期前都可能被冒用。**

所以實務上 Access Token 效期設短，再搭配 Refresh Token 換發。
